# アーキテクチャ

```text
read-only Codex JSONL / Rei SQLite・JSONL / Claude JSONL → normalized events → SQLite transactions
                                                 ↓ replay by session/turn
                                       projects / sessions / turns / intervals
                                                 ↓ UTC + IANA zone aggregation
                                      Tauri commands/events → React calendars
```

RustコアはTauriから分離しています。`parser` は1行の正規化、`migrations` はDB構造の検証・バックアップ・段階移行、`claude` はClaudeログのメタデータ抽出と推定区間への変換、`store` は増分走査・重複除去・ターン再構築、`activity` はUTC区間の和集合と日別分割を担当します。`desktop` はアプリ保存先、IPC、監視を担当します。`--no-default-features` でWebViewなしのコアをテストできます。

ReactはIPCから受け取ったデータを安全なテキストとして描画します。日付移動・フィルタ・重複配置・表示期間にクリップした集計を `calendar.ts` に分離しています。バックエンド集計とUI計算は共通の合成フィクスチャで日跨ぎ・重複・DST・欠落日を照合します。UI向けsnapshotでは未使用の日次集計を計算・転送せず、コアAPIのsnapshotでは日次集計を利用できます。フロントエンドから任意パスの読み取りやコマンド実行はできません。ログ参照はDBに記録済みのターンIDから出典を解決します。

読み込みは `spawn_blocking` でUIスレッドから外します。独立した4ファイルまでRayonで並行解析し、DBは単一Mutexとトランザクションで直列化します。監視はnotify、600ms debounce、更新が続く場合は5秒以内、30秒の再走査で補完します。進捗と更新はローカルTauriイベントです。Claude取り込み中もファイルごとに進捗を通知します。警告と失敗は別チャネルで扱い、手動同期の警告は戻り値、自動同期の警告はイベントから表示します。監視の初期化・開始失敗は警告として通知し、監視できない場合も30秒ごとの再走査を続けます。設定保存の同期ロックとDB書き込みもblocking workerで実行します。

## ライブラリ選定

2026-11-21の実環境でnpmレジストリとCargoの解決結果を確認し、安定リリースをロックファイルに固定しました。React 19系、Vite 8系、Tailwind 4系、Vitest 5系、Tauri 2系、rusqlite 0.38、chrono / chrono-tz、notify 8、Luxon 3を採用。正確なバージョンは package-lock.json / Cargo.lock を正とします。Node 24とRust 1.99.1 MSVCでビルドを検証しています。

FullCalendar Standardの非Premiumプラグインは [公式ライセンス](https://fullcalendar.io/license) でMITと確認しました。今回は編集やドラッグが不要であり、未知終了のマーカー・日ごとのDST目盛り・全重複区間の表示を小さな依存で制御するため、React/CSS Gridの代替カレンダーを採用しました。FullCalendarのtimeGridWeek自体の実装検証は採用外のため行っていません。

## プライバシー

ネットワーク通信プラグイン、ファイルシステムプラグイン、シェルプラグインは導入していません。Tauri権限はローカルイベント購読/解除のみです。CSPは自身のアセットとIPCに限定しています。原本は `File::open` の読み取りのみ。DBは依頼文（上限16Ki文字）・必要なイベント・オフセットを保持し、ツール引数・出力・推論本文を保存しません。Codex依頼文の切り詰めは診断へ記録します。Claudeでは会話本文を保存せず、活動種別・cwd・ブランチ・親セッションID・出典パス等のメタデータを保持します。DBと生ログ抜粋は秘密を含み得るローカルデータです。

## 次の改善

現在は同期時に正規化キャッシュから派生テーブルを再構築します。巨大履歴にはセッション単位の再構築と期間限定IPCを追加できます。OS固有の保存場所と監視処理はdesktop層に閉じ、パーサーはPath/UTCを使用します。

## ローカル保存先

端末固有ログの派生DBには `app_local_data_dir()` を使用します。WindowsはAppData/Local、macOSはLibrary/Application Support、LinuxはXDG_DATA_HOME（既定 .local/share）です。Windowsの旧Roaming保存先からは、LocalにDBがない場合だけSQLite backup APIでWALを含む整合したコピーを作り、上書き禁止の確定処理を使います。旧DBは削除しません。CODECAL_DATA_DIRを明示した場合は指定先だけを使い、通常プロファイルから移行しません。

## カレンダーの表示モデル

日・週・月は同一の日別インデックスを参照します。履歴、プロジェクト絞り込み、タイムゾーンの変更時にだけ区間分割と日次和集合を再計算し、月の各セルで全履歴を再走査しません。月は7列（曜日）と4〜6行（週）の配置です。ビューと表示日の変更は、スピナーを描画するフレームを確保した後、Reactのtransitionで反映します。

## ウィンドウ状態の保存と復元

Tauri公式のtauri-plugin-window-state 2.5をRust側へ登録し、位置・サイズ・最大化状態を通常終了時に保存、起動時に復元します。状態ファイルはDBと同じLocal保存先のwindow-state.jsonです。CODECAL_DATA_DIRによる隔離にも従います。ゲストJS APIは使わず、フロントエンドの権限は増やしていません。

DBの実パスから状態ファイルの絶対パスを作り、公式プラグインのwith_filenameへ渡します。Tauriは通常の設定ウィンドウをapp.setupより前に生成するため、メインウィンドウのcreateをfalseにし、プラグイン登録後にWebviewWindowBuilder::from_configで生成しています。visibleもfalseにし、プラグインが位置・サイズを復元した後に表示します。これにより初期化順序の不備と起動時の位置のちらつきを避けます。

プラグインの保存対象はSIZE / POSITION / MAXIMIZED / VISIBLE。状態ファイルがない・壊れている場合は初期状態で開き、保存位置に対応するモニターがない場合はOSの配置を使います。自前のウィンドウ状態パーサーや移動イベント処理は追加していません。

公式仕様: https://v2.tauri.app/plugin/window-state/

## れいの読み取り

`rei` はSQLite・旧JSONLを共通イベントへ正規化します。時間集計とカレンダーは既存処理を使い、同じ作業パスは同じプロジェクトへ集約します。設定・監視・診断・出典表示も取得元ごとに扱います。保存形式と互換性は [れいの実行履歴](rei-history.md) を参照してください。

人間の観測は `rei_human` が別経路で読みます。SQLite 内で種別を正規化し、時刻・推定継続時間・同期IDだけを投影します。
256行ずつ整合した原本スナップショットを読み、許可情報だけを私有一時DBへ蓄積します。この全件確認中に画面用StoreのMutexを保持する設計にはしません。
最小化済み一時DBとキャッシュを native_id 順に一度ずつ読み、差分と変更前の開始時刻だけをディスク上のTEMP表へ取り出します。
Rei原本はCodeCal DBへATTACHしません。通常の差分確認用読み取りを閉じてから、キャッシュ反映のトランザクションを開始します。全ソースの人間キャッシュが空で、観測開始が原本rowid順に非減少の場合だけ、最小化済み一時DBを `mode=ro` で接続してSQLite内で一括挿入します。接続APIは非公開のHumanStageだけを受け取り、原本パスは渡せません。読み取り専用を検証し、成功・失敗・取消しの全経路で切り離します。
同一ソースの少数変更では該当時刻と前観測だけ、大量変更では索引順の走査で実効終了を確定します。
`human_runtime` は専用の単一 worker と原本接続を持ち、既存 Store Mutex を保持せずに走査します。保持接続の data_version、DB/WAL のファイル監視、30秒の補完確認、600msの通知集約と自動同期の最小1秒間隔を使います。手動同期は全確認です。
設定操作用の直列化ロック、差分確認〜commit/期間取得/設定保存/削除用の確定ゲート、小さい制御状態の Mutex と原子的な設定世代を分けています。原本走査は確定ゲートの外で行い、確定前にも世代を照合します。設定保存失敗では世代を変えません。
Rei の監視は人間のみなら storage.db/-wal の固定ファイルだけ、AI有効時は projects.json と projects 配下も対象にします。両方OFFで Rei の監視を外します。物理IDの変化により監視を張り直し、ファイル出現は固定パスの再確認で検知します。
専用 IPC は human_activity(from,to)、human_status、sync_human、clear_human_activity(all)。人間を既存全件 snapshotへ追加しません。状態イベントも設定世代を持ち、React の期間フックは別期間・別設定・古い世代の結果を棄却します。
一時DBはCodeCalデータディレクトリの human-staging に論理ソースパスのハッシュ付き名で置き、通常は自動破棄します。履歴削除では設定OFFとキャッシュ削除を同じtransactionで確定し、旧workerが停止してから対象ソースの残存ファイルを回収します。リンク/再解析ポイントの管理ディレクトリを回収先にせず、未完了を通知します。
期間応答は時刻と種別・固定診断だけで、source_id/native_id/ソースパスは公開しません。詳細は [設計](human-activity-design.md) を参照してください。

## 人間の表示・集計

`human_summary` は最大62日分の種別ごとの区間和集合と選択種別の総和集合を、観測数に依存しない日別状態で計算します。月画面は全記録をIPCへ送らず、この要約と必要な日の遅延取得を使います。日・週の `human_activity` は50,000出力行を上限とし、超過時は明示エラーを返します。同種の連続区間は出力上限の判定前にまとめます。分類を非表示にしても、元の区間確定を変更しません。

AIと人間の時間帯は共通の重なり配置を使い、詳細モデル・集計・フィルタは分離します。期間フックは設定世代・期間キー・要求番号で古い応答を棄却し、OFFやソース変更、取得失敗で表示済みデータを除去します。現在パスが識別不能な別オブジェクトの場合は旧物理ファイルの履歴へフォールバックしません。原本が実際に消えた場合は直前の正常キャッシュを保持します。

起動と設定保存はバックエンドの構成更新による人間同期を使い、画面のAI同期から重複して強制走査しません。手動の同期ボタンでは人間にも強制更新を要求します。workerのSQLiteページキャッシュは32MiBまでとし、一時領域とソートを含む実測メモリは性能文書で検証します。
